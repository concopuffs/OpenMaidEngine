# Launcher — implementation plan

**Date:** 2026-11-15
**Spec:** `docs/superpowers/specs/2026-11-15-launcher-design.md` (cited as "spec §n"). The spec stays the design's
home. This plan keeps what each milestone measures and builds, and what that settles for the later ones.
**Status:** M0 measured on 2026-11-15 (§3), and the user accepted its recommendations (§3.12); M1 in progress;
M2 to M4 are outlines.
**Branch:** `feature/launcher`, off `develop` at `3796f94c`.

Paths are relative to `age-reimpl/`.

## 1. What the code says today

Before planning, the spec's claims about the engine that M1 relies on were checked against the code. They hold.
The details matter for the tasks below:

- **Repeated options.** The Godot host takes the last value: `ArgumentValue` (`godot/Main.Drive.cs`) uses
  `LastIndexOf`, and `GameRootSelection`, `GameProfileSelection` and `AssetLaunchOptions` overwrite in a loop.
  `Ome.Cli` takes the first: its `OptionValue` (`engine/Ome.Cli/Program.cs`) uses `Array.IndexOf` for
  `--game-root` and `--data-root`. Inside `Ome.Cli` itself the two rules meet: the conventional game root follows
  the first `--profile`, while `GameProfileSelection.Resolve` picks the last.
- **The start order** (`godot/Main.cs` `_Ready`): game root, asset options, catalog identity, game selection,
  engine build, catalog, persistence (with `--data-root`), then `LinkMods` (`godot/Main.Mods.cs`), which can
  write `mods/selectors.toml` (`--forget-mod`, a link), `mods/.cache/` and `diagnostics/mod-link.txt`. Then
  `LoadPortOptions` opens `OME.INI` through `OmeIniStore.For(user://, --data-root)`, and saves open after that.
  The run lock therefore goes right after the persistence is resolved and before `LinkMods`.
- **`[launch]` flags** are read in `Main.cs` itself: `--render-backend` and `--text-backend` in the option loop,
  `--lua-errors` near the end of `_Ready`.
- **Discovery hashes every candidate.** `ModLaunch.Discover` calls `ModPackage.Open`, which computes the package
  hash on open.
- **The skip-failed cache key** (`ModStack.SkipFailedKey`) covers the packages discovery opened: every candidate
  but those `load-order.txt` disables. With the new discovery only enabled packages open, so the key covers them
  by construction; M1 adds the mode to it.
- **A link that writes nothing exists already** for `omp check`: `OmpCommands.LinkForInspection` (internal) links
  with the kept selectors and writes no cache and no selector. M2's inspection link (spec §5.9) starts from it.
- **The link base.** `ModLinkBase.ForInstall` is in `Ome.Mods` already. The host passes the opcode table and
  contracts embedded in the Godot assembly (`godot/OmeRuntimeMetadata.cs`, from `build/opcodes.json`); `Ome.Cli`
  passes the same file read live (`Paths.OpcodesJson`). Both pass the repository's globals, OMS modules and patch
  points when they exist.
- **The base mods target `extended`** (`mods/*-base/manifest.toml`), so a Compatibility profile's refusal of a
  package that requires one follows from the rule.
- **`OME.INI` under `--data-root`** is the one beside the saves (`OmeIniStore.For`): a profile gets its own with no
  change.
- **Python's prefix matching.** `tools/paths.py` reads `--profile`, `--game-root` and `--extracted-root` with
  `argparse`'s default `allow_abbrev=True`, so `--game X` is read as `--game-root X` today.
- **The driver** (`tools/drive_port.py`) always starts `--game-root <install> --data-root <sandbox>`, and
  `drive_core.prepare_sandbox` seeds with `shutil.copytree` of the whole profile root.
- **Godot's user folder.** `godot/project.godot` names the project "Open Maid Engine" and sets no custom user
  folder, so `user://` is `%APPDATA%\Godot\app_userdata\Open Maid Engine` on Windows and
  `$XDG_DATA_HOME/godot/app_userdata/Open Maid Engine` on Linux, for the editor run and the export alike.
- **The SDK.** `global.json` pins SDK 8.0.408 (`rollForward: latestPatch`). This machine has SDKs 5.0 and 8.0 and
  the .NET 10.0.8 runtime, no .NET 10 SDK. WSL has an Ubuntu distribution.

One point in the spec read two ways, the path placeholder `<profile>`; the user settled it (§7, question 1).

## 2. Milestone 0: measurement

M0 builds no product code. It answers the questions the spec leaves to it (spec §10, §14) with measurements, and
records them in §3 of this plan.

### 2.1 The spike

`launcher/Ome.Launcher.Spike/`: a bare Avalonia program, in no solution and not shipped, as the Lua spike was
(`engine/Ome.Scripting.Lua.Spike/`). It has:

- **a window** showing a Japanese title (姫狩りダンジョンマイスター) in Noto Sans JP, loaded from
  `godot/assets/NotoSansJP-Regular.otf` as an embedded font, and a log line with the time from process start to
  the window's first frame;
- **`--check-like`**: a path that returns before Avalonia starts, prints a few lines and exits 1, as the real
  `--check` will (spec §8.6);
- **`--capture PROGRAM ARG…`**: starts a program with its standard output and error redirected, writes what
  arrives to a file with the time of each line, and prints the exit code;
- **`--lock PATH [--hold-until-killed] [--ready FILE]`**: opens `PATH` with `FileShare.None`, sets its last-write
  time through the held handle (`File.SetLastWriteTimeUtc(SafeFileHandle, …)`), writes a readiness file, and holds
  it; without `--hold-until-killed` it reports whether the open succeeded and exits.

The spike references no engine project, so its numbers are Avalonia's and the runtime's alone. M2 measures the
real launcher's size again with the engine libraries.

## 3. Milestone 0 results

Measured on 2026-11-15 with the spike (`launcher/Ome.Launcher.Spike/`, Avalonia 12.1.6 on net10.0, SDK 10.0.404).
Windows: this machine (Windows 10 19045, RTX 4080 SUPER). Linux: WSL2 Ubuntu 20.04 (glibc 2.31) under WSLg, built
on ext4. The scripts are in `launcher/Ome.Launcher.Spike/measure/`; their raw results are in disposable
`build/launcher-m0/results-*.json`. Every publish is self-contained, without debug symbols. SkiaSharp's and
HarfBuzzSharp's native packages publish their native libraries' symbols (100 MiB on win-x64); the spike drops them,
as a release must. "First" is the first start after publishing, not a cold boot; "warm" is the median of the next
five.

### 3.1 Size and start time (question 1)

| Variant | Windows: files / folder / zip | start first / warm | Linux: files / folder / tar.gz | start first / warm |
|---|---|---|---|---|
| folder | 220 / 107.9 MiB / 48.3 MiB | 676 / 580 ms | 219 / 105.3 MiB / 45.9 MiB | 594 / 442 ms |
| single file, natives beside | 4 / 101.2 / 44.6 | 617 / 578 | 3 / 96.7 / 42.5 | 488 / 499 |
| single file, natives unpacked | 1 / 101.2 / 44.6 | 625 / 577 | 1 / 96.7 / 42.5 | 446 / 475 |
| single file, compressed | 1 / 50.7 / 44.7 | 717 / 615 | 1 / 50.4 / 42.8 | 532 / 512 |
| single file, ReadyToRun | 4 / 141.2 / 59.0 | 357 / 325 | 3 / 137.2 / 57.2 | 215 / 222 |
| single file, partly trimmed (Windows only) | 4 / 41.5 / 19.0 | 799 (one start) | | |

- **Noto Sans JP** draws the Japanese titles from the font embedded as an Avalonia resource (the window's own
  screenshot, `build/launcher-m0/window-*.png`); the font resolves by its family name. It adds 4.3 MiB to the
  program.
- **The archives grow by about 60 %.** v0.6.0's Windows zip is 76.5 MiB and its Linux `.tar.gz` 65.8 MiB; the
  launcher adds 44.6 and 42.5 MiB. The engine's own .NET runtime cannot be shared (spec §10).
- **Compression** saves nothing in an archive and costs up to 40 ms. **ReadyToRun** saves about 250 ms per start for
  14.5 MiB per archive, but its publish needs 2.3 to 2.7 GiB (§3.7).
- **Partial trimming** (`TrimMode=partial`, which trims only .NET's own assemblies) brings the zip to 19.0 MiB and
  the window still draws. Spec §10 rules trimming out because the engine libraries are not written for it; the
  spike references none of them, so this number says nothing about their safety.

**Decides:** a single file with the native libraries beside it. It starts as fast as the other forms, unpacks
nothing (§3.3), and costs no more in the archive. No compression; no ReadyToRun (§3.7). Trimming stays out, as the
spec says; the number is recorded for the user (§3.12).

### 3.2 A Windows program cross-built on Linux (question 2)

The SDK 10 publish of `win-x64` on Linux embeds the icon, the version resource and the manifest
(`measure/pe-resources.ps1`: `RT_ICON`, `RT_GROUP_ICON`, `RT_VERSION`, `RT_MANIFEST` with PerMonitorV2, the UTF-8
code page and the supported OS), the same as the publish on Windows, for the folder, the single file and
ReadyToRun. No `NETSDK1074`. The cross-built programs run on Windows. The one difference, a ProductVersion without
the commit hash, comes from building a copy that was not a git checkout.

**Decides:** the release job publishes the Windows launcher on its Linux runner with the SDK alone: no `windres`,
no checked-in `.res`.

### 3.3 Where the native libraries go (question 3)

- **Beside the program** (single file, natives beside): `av_libglesv2.dll`, `libHarfBuzzSharp.dll` and
  `libSkiaSharp.dll` on Windows, `libHarfBuzzSharp.so` and `libSkiaSharp.so` on Linux, loaded from the program's
  folder. Nothing is written elsewhere.
- **Unpacked** (`IncludeNativeLibrariesForSelfExtract`): on the first start they are written to
  `%TEMP%\.net\<program>\<hash>\` on Windows and `~/.net/<program>/<hash>/` on Linux, and loaded from there;
  `DOTNET_BUNDLE_EXTRACT_BASE_DIR` moves that folder. That is a write outside a portable home on every machine
  the program runs on.

**Decides:** natives beside the program (§3.1), so a portable home's promise (spec §4.1) holds for the launcher.
They sit beside `OME.exe` / `OME`; none of their names is one the engine loads.

**What the engine writes outside a portable home** (spec §4.1 asks M0 to list it): v0.6.0, started with
`--data-root`, wrote only Godot's `logs/` (its rotated `godot.log`) and `shader_cache/` (about 1 MB) under
`%APPDATA%\Godot\app_userdata\Open Maid Engine\`.

### 3.4 Linux system libraries and the glibc floor (question 4)

- **glibc:** the newest version any published file needs is 2.27 (`libSkiaSharp.so`, `libcoreclr.so`,
  `libclrjit.so`); the program itself needs 2.16. The engine's floor is 2.28 (its FFmpeg bundle,
  `docs/platform-portability.md`), so the launcher does not raise it.
- **`ldd`** resolves everything but `libcoreclrtraceptprovider.so`'s `liblttng-ust.so.0`, which .NET loads only for
  tracing.
- **At run time** the window maps, beyond libc: the X11 client libraries (`libX11`, `libX11-xcb`, `libxcb`,
  `libXau`, `libXdmcp`, `libXext`, `libXfixes`, `libXi`, `libXrandr`, `libXrender`, `libXcursor`, `libXdamage`,
  `libXxf86vm`), `libICE` and `libSM`, `libfontconfig` and `libfreetype`, GL (glvnd and Mesa), and ICU
  (`libicu66`), the last because the spike keeps globalization on. These come with any desktop distribution; the
  Linux archive's README names them.
- **`--check-like` with neither `DISPLAY` nor `WAYLAND_DISPLAY`** prints its lines and exits 1, from the folder and
  from the single file.

**Decides:** the launcher's command line works with no display; the Linux archive needs no new floor.

### 3.5 The launcher's output on Windows (question 5)

A windowed program that calls `AttachConsole(ATTACH_PARENT_PROCESS)` when it has no standard output prints into the
console it was started from; the handles are usable right after attaching, so nothing reopens `CONOUT$`. Each case
ran in its own console (`measure/console-windows.ps1`):

| Started from | Does the shell wait? | What arrives |
|---|---|---|
| `cmd /c "… && … \|\| …"` | yes; `&&` sees exit 1 | every line, in the console |
| a batch file | yes; `%ERRORLEVEL%` is 1 | every line |
| `start "" /wait …` | yes, but `&&` after `start` reads 0 | every line |
| cmd at its prompt | no: the prompt comes back first, the lines after it | every line, after the prompt |
| PowerShell, plain | no: `$LASTEXITCODE` stays empty, the lines come after | every line, after |
| PowerShell, `Start-Process -Wait -PassThru` (with or without `-NoNewWindow`) | yes; `ExitCode` is 1 | every line |
| PowerShell, piped (`\| Out-Host`) | yes; `$LASTEXITCODE` is 1 | standard error is lost; non-ASCII is garbled (PowerShell 5.1 decodes the pipe as cp932) |
| a captured .NET process | yes | every line on its stream, UTF-8 intact |
| `--output FILE` | | every line, UTF-8 intact |

On a console, text is written in the console's code page: Japanese survives cp932, an em dash prints as `?`.

**Decides:** `docs/tools-reference.md` (M2) gives `Start-Process -Wait -PassThru` for PowerShell, a batch file or
`start /wait` for cmd, and `--output FILE` as the form for scripts, as spec §8.6 has it.

### 3.6 Capturing a release engine (question 6) and a second start (question 7)

- **Windows:** v0.6.0's `OME.exe` (a windowed program) started by a .NET parent with redirected standard output and
  error: `--headless -- --package-smoke` gives its three lines and exit 0; a real start on the Himegari install
  gives every line, live, as it happens (Godot's banner at 38 ms, the `[profile]`, `[assets]` and `[options]`
  lines at 1.7 s, each movie's start), in UTF-8. Godot's warnings arrive on standard error.
- **Linux:** v0.6.0's `OME` gives the package smoke's lines and exit 0. A real start under WSLg (Vulkan missing,
  Godot falls back to OpenGL on llvmpipe) gives Godot's warnings on standard error as they happen and its banner,
  and then **none of the engine's lines** in 25 seconds: a release build does not flush standard output after a
  print (Godot's `application/run/flush_stdout_on_print` is false by default, true only for debug builds, and
  `godot/project.godot` does not set it), so into a pipe the lines wait in stdio's buffer and a killed engine loses
  them. Started through `stdbuf -oL`, the same start gives every line live (24 lines from 1.0 s on).
- **Godot's own log** (`user://logs/godot.log`) stays empty when the engine is killed: it is not flushed either.
  The captured log keeps every line that reached the pipe.
- **Two v0.6.0 engines on one data root** both run. In 20 seconds of the opening movie the only collision was the
  page map, which the second could not open ("being used by another process") and so kept none, with a warning on
  standard error. Saves and settings were not written in that time; nothing in v0.6.0 stops a second start.

**Decides:** spec §8.5 as written: the launcher captures the engine's output into `diagnostics/engine.log`; the
fallback to a per-start `--log-file` is not needed. On Linux the capture needs the engine to flush its output: M1
sets `application/run/flush_stdout_on_print=true` in `godot/project.godot` (§4.12), so an exported engine flushes
after each print on both systems (§3.12).

### 3.7 Memory of the publish (question 10)

A clean `dotnet publish` in WSL with the release build's low-memory flags (`--disable-build-servers`,
`UseSharedCompilation=false`, `-nodeReuse:false`, `-m:1`), the NuGet cache warm:

| Publish | peak, whole process tree | peak, largest process |
|---|---|---|
| linux-x64: folder, single file, unpacked, compressed | 458–478 MiB | 311–450 MiB |
| win-x64 cross-built: folder, single file | 450–464 MiB | |
| ReadyToRun (linux-x64; win-x64 cross-built) | 2,626 MiB; 2,697 MiB | 2,335 MiB |
| ReadyToRun, crossgen2 `--parallelism` 1 and 2 | 2,482 MiB; 2,308 MiB | 2,208 MiB; 2,042 MiB |

The runner kills at about 1 GiB, and Godot's export alone peaks at 772 MiB (`docs/platform-portability.md`).

**Decides:** the launcher's publish fits the runner on its own, not beside Godot's export: the release job runs it
as a step of its own, before or after the export, never inside it. ReadyToRun does not fit, with or without a
limit on crossgen2's parallelism.

### 3.8 The exclusive lock (question 8)

- **Windows:** a second `FileShare.None` open fails with a sharing violation (`0x80070020`) and leaves the file's
  time alone; the holder sets the time through its handle; a killed holder leaves the file, and the next open takes
  it and moves the time. While the lock is held its time can be read, but the file cannot be read, opened even for
  shared reading, or copied: copying a running profile's folder stops at `run.lock`.
- **Linux, on ext4 and on `/mnt` (a Windows drive in WSL):** a second open fails (`EAGAIN`, HResult `0xb`) and
  leaves the time alone; a killed holder leaves the file, and the next open takes it and moves the time. Unlike
  Windows, a plain read of the held file succeeds. .NET emulates `FileShare.None` there with an advisory `flock`:
  every .NET open honours it, other programs need not, and `DOTNET_SYSTEM_IO_DISABLEFILELOCKING=1` turns it off.
  On `/mnt` the time set through the handle is kept to the whole second.

**Decides:** spec §5.5 as written, on both systems. Only a held lock means "running": the engine and the launcher
both open it through .NET, so the advisory lock is enough between them.

### 3.9 Godot's flags through a shortcut (question 9)

A `.lnk` made with `WScript.Shell`, target v0.6.0's `OME.exe`, arguments `--rendering-driver d3d12 -- --game-root …
--data-root … --windowed`, opened as Explorer opens it: the engine loads `D3D12.dll` and `D3D12Core.dll`, and no
`vulkan-1.dll`. **Decides:** spec §8.4's Direct3D 12 setting works from a shortcut as written.

### 3.12 For the user

The user accepted all four recommendations on 2026-11-15: the SDK pin moves to 10.0.4xx with the engine on net8.0,
Avalonia's build telemetry is excluded in every launcher project, the archive growth is accepted without trimming,
and the engine flushes its output after each print (§4.12). The pin moves with the first project that targets
net10.0 (M2). It needs SDK 10 wherever the repository is built: on this machine SDK 10 is installed privately and
off `PATH`, and its folder has no .NET 8 runtime for the tests, so that move starts by asking the user how SDK 10
is to be installed for everyday builds.

1. **The SDK.** The launcher targets net10.0 (.NET 8 is out of support, and a self-contained launcher ships its
   runtime). That needs SDK 10 for every build of the repository that includes the launcher: `global.json` moves
   to 10.0.4xx, the engine projects keep net8.0, CI installs SDK 10 and the .NET 8 runtime for the tests. The
   measured cost is nothing (§3.10). Moving the engine itself to net10.0 stays the backlog's item.
2. **Avalonia's build telemetry** is excluded in every launcher project as the spike does it (§3.10), unless the
   user wants otherwise.
3. **The archive grows by about 60 %** (§3.1). Partial trimming would cut the launcher to 19 MiB per archive, but
   the spec rules trimming out and the engine libraries' trim safety is unknown; it stays out unless the user
   reopens it.
4. **The engine flushes its output after each print** (§3.6, §4.12): a one-line engine change the spec did not
   name, without which the launcher's log of a Linux engine loses what a crash most needs.

## 4. Milestone 1: engine

M1 is spec §5. It is useful without a launcher: a profile folder starts from a shortcut. Gates 1 to 6 (spec §13).
The tasks are in build order; each one is a commit with its tests and the docs it changes.

### 4.1 `--game` (spec §5.8)

**Done 2026-11-15.** One reader, `GameProfileSelection.RequestedGameId`, serves the host's selection, `Ome.Cli`'s
conventional game root and `save-diff`. Beyond the list below: `validate.py`'s own parser is exact too (a prefix
the common parser no longer takes would otherwise reach its help-only `--game-root`), and every tool's usage text
and child invocation says `--game`.

First, because every later task's messages and docs use the new word.

- `GameProfileSelection` accepts `--game ID` and `--profile ID` as one option, last one wins. Messages say "game"
  and name `--game`: unknown id, mismatch, `--probe` without a game, no match, several matches.
  `GameProfileSelectionTests` follows.
- `Ome.Cli`: the conventional game root follows the same last value (it reads the first today). `omp save-diff`
  (`SaveDiffCommand`) gains `--game` in its own parser.
- The options panel's diagnostics row keeps its key; its English and Japanese labels say "game".
- `tools/paths.py`: the common parser gets `--game` with `--profile` as its alias (one `dest`), and
  `allow_abbrev=False`, so no prefix is read as a common flag again. `tools/validate.py` and
  `tools/text_geometry_compare.py` get the same alias. A Python test asserts `--game kamidori` selects the game
  and leaves `--game-root` unset.
- `run-godot.ps1`: `-Game` with `[Alias('Profile')]`, passing `--game`.
- **Docs, in the same commit:** every modder guide, `docs/tools-reference.md`, the generated
  `docs/modding/games/README.md` (`modding_games_build.py --build`), and the `AGENTS.md` rule that names the

  literally holds it: `engine/Ome.Engine/Profiles/`, the manifest's `[game] profile` key, JSON keys the tools emit
  and `hello.profile`, type names, and AGE's shared profile.

### 4.2 The profile file and the resolver (spec §4.3, §5.2)

**Done 2026-11-15.** One change from the list below: the normalized list keeps the command line's arguments in
their places and appends the file's equivalents for the options the command line did not give, rather than putting
the equivalents first. The precedence is the same (a run flag wins), and `Ome.Cli`'s positional arguments
(`args[0]` is the command, `omp build DIR` reads `args[2]`) stay where they are. `ManifestReader`'s `TableReader`
moved to its own internal file so `profile.toml` reads with the same strictness and messages. The `[mods]` table is
parsed and carried in `ResolvedRun.Mods`; discovery follows it in §4.5. A relative `--data-root` now resolves
against the launch directory, as `--game-root` and `--mod` do (on Linux the caller's, where before it was the
process's).

New in `engine/Ome.Mods/Launch/`:

- **`ProfileFile`**: reads `profile.toml` with Tomlyn (the engine's TOML reader, already in `Ome.Mods`), strict as
  a package manifest: an unknown key or table outside `[launcher]` is an error, every value is typed, `mode`,
  `renderer`, `text_backend`, `lua_errors` and `on_failure` are closed sets, and a format version other than 1
  stops with the version it reads. Paths resolve against the profile root, and `[install] overlays` against the
  install root. `[launcher]` is read as an opaque table and ignored. A writer comes in M2.
- **`RunResolver`**: the one resolver of the command line and the profile file, for the host and `Ome.Cli`. It
  returns a `ResolvedRun`:
  - **`Arguments`**: a normalized argument list. With a profile file, it starts with the file's equivalents
    (`--game-root`, `--game`, `--overlay-root`…, `--allow-bmp-as-agf`, `--render-backend`, `--text-backend`,
    `--lua-errors`), and then the command line's own arguments, so a run-only flag wins as the last value. Every
    single-valued option it knows (`--game`/`--profile`, `--game-root`, `--data-root` and the run options) keeps
    one occurrence, the last, so the host's and `Ome.Cli`'s readers cannot disagree. Repeatable options pass
    through in order.
  - **the profile file**, its path, and the values in effect, for the `[profile-file]` log line;
  - **the mods source**: the data root's `mods/` folder as today, or the file's `[mods]` table.
  - **refusals**: with a profile file, `--game`/`--profile`, `--game-root`, `--overlay-root`,
    `--allow-bmp-as-agf` and `--probe` stop with their reason (spec §5.2's table).

  Feeding the existing selections a normalized list keeps one parser per option and gives gate 1 ("the same
  `[profile]`, `[assets]` and `[options]` lines as the equivalent flags") by construction. A profile file still
  holds no engine arguments: the resolver maps typed keys to flags it owns.
- **The strict identity check.** With a profile file, a game whose manifest does not match the install's
  `SYS4INI.BIN` header stops startup. Without one, `GameProfileSelection` keeps today's read-only continuation.
- **The fingerprint.** A recorded `[install] fingerprint` that differs prints a warning and continues.
- **The host** (`godot/Main.cs`) calls the resolver first and reads `run.Arguments` wherever it read `userArgs`;
  a refusal exits with code 2 as other startup errors do. **`Ome.Cli`** (`Program.cs`) calls it before choosing
  the game root, and its `OptionValue` reads the normalized list.

Tests (gate 1): each key's effect equals its flag's; each row of spec §5.2's table; last-wins for `--game` and
`--profile` in both programs; an unknown key, an arguments or environment table, a wrong game and an unknown
version each stop with their reason; relative paths resolve as the spec says.

### 4.3 Checking the root (spec §5.2, §12)

**Done 2026-11-15.**
- The link walk runs before `profile.toml` is read, and sees hidden and system entries.
- The network check runs before the install is read. It covers `install.root`, the overlays and the mod folders. A
  path inside the profile root needs no approval, and `\\?\UNC\…` counts as a network path.
- `MachineState` lives in `Ome.Mods/Launch/`. `machine.toml` holds `ome_machine = 1` and `[network] approved`; the
  cache value joins it in §4.6.
- The host's self-test prints `machine-folder=ok`. A host run stopped on a junction and on an unapproved
  `\\….invalid\…` install, before anything on the share was opened.
- No synthetic placeholder could be made without registering a sync root, so the backlog has that gap.

New `RootSafety` in `Ome.Mods/Launch/`, run by the resolver before anything in the root is opened:

- **Network paths.** On Windows a path that starts with `\\` (or `//`) is a network path. With a profile file,
  each one the file names must be in the machine's approved list, or startup stops and names it.
  `--allow-network-paths` approves the file's network paths for one run. A drive letter and a Linux mount are
  ordinary paths.
- **Links.** With a profile file, a symbolic link or junction anywhere inside the root stops startup. The walk
  does not follow links, and uses `FileSystemInfo.LinkTarget`, which is set for symbolic links and junctions and
  not for cloud placeholders (the spec's "a cloud folder's placeholders are not links"). M1 tests a OneDrive-style
  placeholder only if one can be made synthetically; otherwise the backlog gets the gap.
- **The machine's own state.** New `MachineState` in `Ome.Mods`: Godot's user folder for this project, computed by
  the rule of §1 for `Ome.Cli` and the launcher, and passed in by the host from `ProjectSettings.GlobalizePath`.
  It holds `machine.toml` with the random cache value (§4.6) and the approved network locations. The host's
  self-test checks that its computed folder equals Godot's.

Tests (part of gate 14, which closes in M2): a root with a link stops; a network path not approved stops and is
not opened; an approved one passes; a profile root and an OME home brought from elsewhere carry no approval.
Links are made with `Directory.CreateSymbolicLink` on Linux and as junctions on Windows (a junction needs no
privilege).

### 4.4 The run lock (spec §5.5)

**Done 2026-11-15.**
- **`RunLock`:** `TryAcquire(dataRoot, markStart, out held, out refusal)`. It creates a missing root.
  - `markStart` sets the time; the engine passes true, and the launcher will pass false.
  - `RunLockRefusal.HeldElsewhere` tells another holder (a sharing or lock violation; `EWOULDBLOCK`) from a root
    that cannot hold the file.
- **The host** takes the lock on `ResolvedGamePersistence.ProfileRoot` before `LinkMods`. A held root stops with
  exit 2, having changed no file (checked by hand against an `Ome.Cli` holder).
- **The helper** is `Ome.Cli run-lock DATA_ROOT [--hold]`. It says `held PATH` on its standard output, and the
  tests block on that line in place of a readiness file. It holds until its standard input closes, so a failed
  test leaves no holder behind. `Ome.Engine.Tests` builds `Ome.Cli` through a reference that does not load it.
- **For M2:** when the launcher's own hold (`markStart: false`) is the first open of a root, it creates `run.lock`,
  and the new file's time is the moment of that write. The "last played" display must not read that time as a
  start.

- **`RunLock`** in `Ome.Mods/Launch/`: opens `<data root>/run.lock` with `FileShare.None`, keeps the stream for the
  process's life, and sets the file's last-write time through the held handle once it holds it. `TryAcquire`
  returns the lock or why it failed; the launcher uses the same class in M2. The form follows M0's question 8.
- **The host** takes it right after the persistence is resolved (§1), on every data root, the default
  `user://games/<game>/` included, and before `LinkMods`. A refused lock stops with code 2 and a message, having
  written nothing.
- **`Ome.Cli`** does not take it: its commands write no file in the root.
- **The driver's seed** leaves `run.lock` and `profile.toml` out (`drive_core.prepare_sandbox`).

Gate 4: across two processes with a readiness file and no sleep, the second is refused and changed no file; a
killed holder's file is not "running"; a seeded sandbox holds no `run.lock`; the time moves when the lock is taken
and not when a start is refused. The two processes are `Ome.Cli` test helpers, not Godot.

### 4.5 Mods from a profile (spec §5.3)

**Done 2026-11-15.**
- **The index** is `PackageIndex.Read` (`Ome.Mods/Packages/`). It walks a folder or reads an `.omp`'s central
  directory, and reads only `manifest.toml`. It shares `ModPackage`'s container open and manifest read.
- **The table's discovery** is `ModLaunch.DiscoverTable`. Its errors set `ModDiscovery.FailedToOpen`, so
  `--skip-failed-mods` drops the mod as it drops one that fails to open.
- **A dependency:** an enabled package blocked by a disabled dependency is left unopened. A `--mod` package's
  dependency gets the same check. A dependency in no folder is left to the link's "not installed" error.
- **Other games:** a candidate for another game is left out only when one for this game has the same id.
- **New notes:** a missing or unreadable mod folder, and each disabled id that a folder holds ("disabled by
  profile.toml").
- **The table's path:** the host's `LinkMods`, `ModLaunch.Run`, `LinkForInspection`, the four `omp` commands and
  `TextCommands.Run` take it as a last argument. `Ome.Cli` passes the resolver's `run.Mods`, and `omp text` reads
  the resolver's data root.
- **Checked by hand:** `omp check` and a host self-test on a profile with a shared folder (a broken file and a
  disabled package beside the enabled one) linked the same one-mod stack. The selectors landed in the profile root.

- **A manifest-only read** for a folder and an `.omp`, under the reader's path and size limits (`ModPackage`,
  `ManifestReader`). It returns the id, version, game, target, requirements and whether the package ships Lua.
  This is the start of spec §5.9's index; its package states are M2's.
- **`ModLaunch.Discover` for a `[mods]` table:** index every folder (normalized, each once); open and hash only the
  ids `order` enables; an unreadable candidate is a note by its file name; a candidate for another game is ignored
  unless enabled. Errors at discovery: an enabled id in no folder, an enabled id found twice, an enabled package
  whose hard dependency is in a folder and not enabled.
- **Base mods.** `ShippedPackages.Required` mounts a base mod for an enabled package that requires it, whatever the
  folders hold; a folder's package with a base mod's id replaces the engine's only when `order` enables it; a base
  mod's id in `order` with no such package is a note.
- **`mods/load-order.txt`** is not read with a `[mods]` table; one that exists gets a note.
- **Every reader follows the table:** the host's early "no mods" test (`Main.Mods.cs`) and `omp check`, `export`,
  `explain`, `lua-stubs` and `text`, through the resolver's mods source. `OmpTextCommand` reads `--data-root` on
  its own today and moves to it.

Gate 2 (spec §13) on synthetic packages in two profile roots that share a folder.

### 4.6 The cache key (spec §5.3, §5.4)

- **Two first starts at once** may each make a value. The last write is kept, and the other's entries miss once.

- **`ModLinkBase`** gains `MachineValue` and `ProfileMode`. The host sets both; `Ome.Cli`'s inspection links write no

- **The mode** joins the skip-failed key (`ModStack.SkipFailedKey`) when a profile file names one.
- The skip-failed key covers the enabled packages only, by the new discovery (§1).

### 4.12 Output the launcher can capture (spec §8.5; M0 §3.6)

`godot/project.godot` sets `application/run/flush_stdout_on_print=true`, so an exported engine flushes its standard
output after each print, as the editor build already does. Without it a Linux engine's output reaches a pipe only
when stdio's buffer fills or the engine exits normally, and a crash loses it. A core test reads the setting from
`project.godot`, so it cannot be dropped silently; the release smoke on Linux captures the exported engine and
checks that its first engine line arrives before it exits. The setting costs one flush per printed line; the engine
prints at startup and per event, not per frame.

## 6. Risks

- **The normalized list hides a flag's origin.** A refused flag must be refused before the profile's equivalents
  join the list, and the `[profile-file]` line names what came from the file.
- **A lock on the default data root** changes the bare engine: two bare engines on one game now refuse the second.
  That is the spec's intent (spec §5.5); `docs/tools-reference.md` says so.
- **The machine value invalidates every cache once.** Harmless, but the first start after the update links again.
- **Windows resources on a cross-built launcher** may need a tool the pipeline lacks (M0 question 2).
